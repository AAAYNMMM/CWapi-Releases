# CWapi 2.0 Agent Guide

[English](AGENT_GUIDE.md) | [简体中文](AGENT_GUIDE.zh-CN.md)

CWapi Agent lets local software that speaks an OpenAI-compatible Chat Completions API use Web GPT as the reasoning/model side of the loop.

It is not a generic reverse proxy to the OpenAI API. The request is held by CWapi's local broker, delivered to Web GPT through Agent MCP, and completed when Web GPT sends the correlated response back.

## Architecture

```text
Local OpenAI-compatible software
        ↓
POST /v1/chat/completions
        ↓
CWapi localhost Provider
        ↓
Bounded Agent broker
        ↓
Agent MCP: agent_exchange
        ↓
ChatGPT Web / Web GPT
        ↓
content and/or tool_calls
        ↓
CWapi Provider response
        ↓
Local software
```

CWapi's local Provider binds only to `127.0.0.1`.

## Local Provider configuration

Default configuration:

```text
Base URL: http://127.0.0.1:32123/v1
Model:    cwapi-web-gpt
API key:  generated by CWapi and available from the GUI
```

If the Agent port was changed, use:

```text
http://127.0.0.1:<agent-port>/v1
```

Implemented endpoints:

```text
GET  /v1/models
POST /v1/chat/completions
```

The Provider uses `Authorization: Bearer <Agent API key>`. A missing or wrong key returns HTTP 401 `invalid_api_key`.

## Supported request shape

The current Chat Completions normalization accepts these top-level request fields:

```text
model
messages
tools
tool_choice
response_format
stream
```

`messages` is required. If `model` is empty, CWapi normalizes it to:

```text
cwapi-web-gpt
```

Unknown top-level fields are rejected rather than silently passed through as if CWapi implemented the entire OpenAI API surface.

This is one reason compatibility with any particular Cline/Roo Code/other client release should be tested rather than assumed.

## Agent MCP tools

The Agent MCP app exposes exactly:

```text
agent_open
agent_exchange
agent_close
```

Web GPT never receives a public `bridge_id`. CWapi owns the internal bridge generation and automatically applies it to exchanges and close operations.

## `agent_open`

Call `agent_open()` at the start of a continuous Agent task.

If there is no active bridge, CWapi opens one. If the bridge is already active, CWapi resumes it and reports `resumed=true`.

The result includes `max_inflight`. The current default is 4.

Do not create a new bridge for every local API request. One active bridge is meant to carry a continuous stream of independent requests.

## `agent_exchange`

The normal loop is:

```text
agent_open()
        ↓
agent_exchange(capacity=4)
        ↓
receive zero or more requests
        ↓
Web GPT produces responses for exact request_id values
        ↓
agent_exchange(responses=[...], capacity=4)
        ↓
CWapi accepts responses and returns next batch
        ↓
repeat
```

If `agent_open` reports a `max_inflight` smaller than 4, use that smaller capacity.

`agent_exchange` is intentionally an atomic “submit finished responses + wait for the next batch” operation. This reduces unnecessary extra MCP round trips.

## `request_id`

Every returned local model request has an exact `request_id`. It is the public correlation key and must be preserved exactly.

Multiple requests may be in flight at the same time, so do not correlate by arrival order, prompt text, client name, or vague human intuition.

A `delivery` value greater than 1 means the **same request_id was redelivered**. It is not new work. If Web GPT already completed that request, safely re-send the same completed response rather than inventing a different one.

## Multiple independent requests

The broker's current defaults are:

```text
maximum active queue: 16
maximum in-flight:     4
request timeout:       180 seconds
exchange JSON batch:   1 MiB
```

When a batch contains independent requests, Web GPT can reason about them together when convenient, but each result must still be returned under its own exact `request_id`.

A failure/rejection for one response item does not automatically roll back successfully accepted siblings. Correct the rejected item and continue.

## Function tools and `tool_calls`

Local OpenAI-compatible coding agents commonly send a `tools` schema and expect the model to return function calls.

CWapi preserves that model loop:

```text
Local software sends tools
        ↓
Web GPT decides which function(s) should be called
        ↓
Web GPT response contains assistant tool_calls
        ↓
CWapi returns tool_calls to local software
        ↓
Local software executes its own local tool(s)
        ↓
Local software sends the tool result in a later Chat Completions request
```

The **Agent GPT does not directly execute the third-party application's local tool**. It returns the `tool_calls`; the local application owns execution and sends resulting tool messages back through the normal API loop.

### Parallel function calls

If one request needs several independent functions and all arguments are already known, return those calls together in the same assistant `tool_calls` array.

Keep calls sequential only when a later tool call genuinely depends on the result of an earlier one. Splitting independent calls across extra model turns wastes time and resends large prompts/tool schemas for no benefit.

## Text responses

A completed response can return normal assistant content. CWapi normalizes the Agent response into the OpenAI-compatible Chat Completions message/finish-reason shape expected by the local client.

Both non-streaming and streaming requests are supported. Streaming responses are emitted as Chat Completions SSE chunks and finish with `[DONE]`.

## Inline images

Agent supports bounded raster images only through the standard Chat Completions message-content form:

```json
{
  "type": "image_url",
  "image_url": {
    "url": "data:image/png;base64,..."
  }
}
```

CWapi:

1. validates the data URI and raster image;
2. removes the raw image bytes from the broker JSON payload;
3. stores the image temporarily for that request;
4. returns attachment metadata plus native MCP `ImageContent` from `agent_exchange`;
5. removes temporary image data on terminal request paths, broker shutdown, and startup cleanup.

Current Agent image limits:

- maximum 8 images;
- maximum 8 MiB per image;
- maximum 16 MiB image batch;
- maximum 2048 px per side;
- raster only; SVG is unsupported.

The HTTP body limit is 24 MiB so base64/JSON overhead can fit. After images are extracted, the normal broker JSON request/batch remains limited to 1 MiB.

## Generic files are not supported

CWapi deliberately rejects a top-level generic file extension such as:

```json
{"attachments": [...]}
```

with:

```text
AGENT_FILE_ATTACHMENTS_UNSUPPORTED
```

Text files, PDFs, archives, office documents, and other generic files are not converted into MCP resources for Agent.

An image/file uploaded to the ChatGPT conversation also has **no reverse path** into the local OpenAI-compatible client. If the local client needs data, it must provide that data through its own supported Chat Completions messages/tools.

## `agent_close`

Call `agent_close()` when the continuous Agent task is truly finished.

Do not close the bridge just because one `agent_exchange` returns `no_request`. A temporarily empty queue is normal.

Closing the bridge makes new local requests unable to enter a usable Web GPT exchange path until Agent is opened again.

## Secure MCP Tunnel for Agent

Agent MCP is a different surface from Coding MCP.

Local endpoints resemble:

```text
Coding MCP: http://127.0.0.1:<mcp-port>/mcp/coding/<coding-token>
Agent MCP:  http://127.0.0.1:<mcp-port>/mcp/agent/<agent-token>
```

If both are used from ChatGPT, configure **two independent OpenAI Secure MCP Tunnels**:

```text
Coding Tunnel -> Coding MCP only
Agent Tunnel  -> Agent MCP only
```

Each has its own:

- Tunnel ID;
- Runtime API key;
- generated tunnel profile;
- `tunnel-client` process;
- local MCP target.

Do not point the Coding Tunnel at Agent MCP or reuse one set of tunnel credentials in both GUI panels.

## HTTP errors from the local Provider

### 401 `invalid_api_key`

The local client sent no Bearer key or the key does not match CWapi's current Agent API key.

### 400

The request body or supported Chat Completions shape is invalid. Examples include malformed JSON, invalid messages/tools/tool choice/response format, or unsupported fields.

### 413 `request_too_large`

The HTTP request body exceeded the 24 MiB hard limit.

### 429 `AGENT_BUSY`

The bounded broker queue is full/busy. Wait for pending or claimed requests to finish before sending more work.

### 503 `AGENT_BRIDGE_UNAVAILABLE`

There is no usable active Agent MCP bridge. Open/resume it in ChatGPT with `agent_open` and keep the exchange loop alive.

Other broker-unavailable conditions can also surface as 503.

### 504 `AGENT_REQUEST_TIMEOUT`

The request did not receive a completed Web GPT response before its deadline. The current default request timeout is 180 seconds.

## Example local request

```http
POST /v1/chat/completions
Authorization: Bearer <CWapi Agent API key>
Content-Type: application/json

{
  "model": "cwapi-web-gpt",
  "messages": [
    {"role": "user", "content": "Explain this error and propose a fix."}
  ]
}
```

While this request is waiting, the Agent Web GPT conversation should be running `agent_exchange` so the broker can deliver it.

## Example function-tool loop

```text
1. Local coding client sends messages + filesystem/search/edit tools.
2. CWapi assigns request_id and agent_exchange delivers the request.
3. Web GPT chooses search_files and read_file, returning assistant tool_calls.
4. CWapi returns those tool_calls to the local coding client.
5. The local client executes those functions locally.
6. The local client sends a new /v1/chat/completions request containing tool results.
7. Web GPT receives that new request through agent_exchange and continues reasoning.
```

The exact local tools belong to the client, not to CWapi Agent MCP.

## Does Agent use Coding automatically?

No. Coding and Agent can run at the same time, but they are isolated surfaces. An Agent Web GPT bridge does not silently gain the Coding tool catalog, and local Agent requests do not automatically operate a CWapi Coding workspace.

If a workflow intentionally needs both apps in ChatGPT, connect both independently and keep their responsibilities clear.

## Where the Agent API key lives

The Agent Provider API key is generated as part of `cwapi.config.v3` and stored in:

```text
CWapi-data/config/cwapi.json
```

The GUI masks/provides it for local client configuration.

This is different from the **Agent Tunnel Runtime API key**, which is stored in Windows Credential Manager.
