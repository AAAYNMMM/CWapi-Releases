# Migrating from CWapi 1.6.3 to 2.0

[English](MIGRATION_FROM_1.6.md) | [简体中文](MIGRATION_FROM_1.6.zh-CN.md)

CWapi 2.0 is **not** a simple in-place upgrade of 1.6.3. The communication architecture was redesigned. Treat migration as setting up a new 2.0 installation while preserving the old installation until your 2.0 workflow is verified.

## What changed

The main transport changed from:

```text
CWapi 1.6.x
Web GPT <-> GitHub + Slack workflow <-> local development process
```

to:

```text
CWapi 2.0 Coding
ChatGPT Web -> Secure MCP Tunnel -> Coding MCP -> durable local Git workspace

CWapi 2.0 Agent
Local OpenAI-compatible client -> CWapi /v1 -> Agent MCP -> Secure MCP Tunnel -> ChatGPT Web
```

This is why the old Slack configuration is not a reusable 2.0 connection profile.

## Do not overwrite the new installation with the old data directory

The 1.6.x and 2.0 configuration schemas are not compatible.

Do **not** copy the complete old `CWapi-data`, config, workspace tree, or credential material over a clean 2.0 installation.

A safer migration is:

```text
C:\Tools\CWapi-1.6.3\...
C:\Tools\CWapi-2.0.2\...
```

Keep both extracted directories separate while testing 2.0. They can coexist because each portable directory has its own adjacent data root.

## What does not migrate

### Slack credentials

These 1.6.x values do not migrate into 2.0:

- Slack App Token;
- Slack Bot Token;
- Slack Channel ID;
- any other Slack-route-specific configuration.

CWapi 2.0 does not use Slack for Coding or Agent.

### Old MCP v2 Slack framing

The MCP v2 framing used inside the 1.6.x Slack workflow is **not** the ChatGPT direct MCP surface used by 2.0.

In 2.0, ChatGPT discovers the public Coding/Agent MCP tools through Secure MCP Tunnel. Do not treat an old Slack frame or bridge identifier as a 2.0 app configuration.

### Old workspace directory as a direct 2.0 import

Both generations have persistence/workspace concepts, but the implementations and directory contracts differ.

Do not copy an old 1.6 workspace directory into `CWapi-data/workspaces/<repository-hash>/repo` and assume it is a supported 2.0 workspace. Preserve important local work with Git commits/pushes or a separate backup, then let 2.0 create/manage its own workspace.

## New 2.0 concepts you must configure

### Coding MCP

2.0 exposes exactly these Coding tools:

```text
coding_open
coding_exec
coding_status
coding_close
```

Web GPT is the only reasoning agent. The bundled Codex runtime is a model-free command/exec toolhost, not a second agent.

### Coding Secure MCP Tunnel

Create a dedicated Secure MCP Tunnel for Coding and configure its:

```text
Tunnel ID
Runtime API key
```

The Tunnel ID is stored in `CWapi-data/config/cwapi.json`. The Coding Runtime API key is stored in Windows Credential Manager under:

```text
CWapi/2.0/OpenAI/Tunnel/APIKey
```

### Agent Provider

2.0 adds a localhost OpenAI-compatible provider:

```text
Base URL: http://127.0.0.1:<agent-port>/v1
Model:    cwapi-web-gpt
```

Implemented endpoints are:

```text
GET  /v1/models
POST /v1/chat/completions
```

The Agent Provider API key is generated by CWapi and stored in `CWapi-data/config/cwapi.json`.

### Agent MCP and Agent Tunnel

If you use Agent, create a second independent Secure MCP Tunnel for the Agent MCP app.

Its Runtime API key is stored separately in Windows Credential Manager:

```text
CWapi/2.0/OpenAI/Tunnel/Agent/APIKey
```

Do not reuse the Coding Tunnel ID/profile for Agent.

## Credential-storage differences

A clean 2.0 installation separates ordinary config from Tunnel Runtime API keys:

Stored in `CWapi-data/config/cwapi.json`:

- Coding MCP token;
- Agent MCP token;
- Agent Provider API key;
- Coding Tunnel ID;
- Agent Tunnel ID;
- other non-secret runtime configuration.

Stored in Windows Credential Manager:

```text
CWapi/2.0/OpenAI/Tunnel/APIKey
CWapi/2.0/OpenAI/Tunnel/Agent/APIKey
```

Do not manually transplant old credential files into the new installation.

## Recommended migration procedure

1. **Finish or preserve important 1.6.3 work.** Commit/push important repository work where appropriate and make a separate backup of anything that must not be lost.
2. **Leave 1.6.3 installed.** Do not modify the working 1.6.x directory yet.
3. **Download and fully extract 2.0.2** into a different user-writable directory: [`CWapi-v2.0.2.zip`](https://github.com/AAAYNMMM/chatgpt-work-api-Releases/releases/download/v2.0.2/CWapi-v2.0.2.zip).
4. **Run CWapi 2.0 once** so it creates its own `CWapi-data` and v3 configuration.
5. **Configure Coding** if needed: create a Coding Secure MCP Tunnel and save its Tunnel ID/Runtime API key through the Coding panel.
6. **Connect the Coding app in ChatGPT** through that Tunnel and confirm the exact four `coding_*` tools appear.
7. **Open a test repository** and verify read-only Coding first, then normal SAFE edits/tests.
8. **Configure Agent separately** if needed: create the second Agent Tunnel, connect the Agent MCP app, and configure your local client with CWapi's Base URL/model/Agent API key.
9. **Verify your real workflow** before retiring 1.6.3.
10. Only after 2.0 is proven for your use case should you archive the old directory. Keep any historical data/credentials according to your own retention needs.

## What should be reconfigured manually?

Plan to configure these again in 2.0:

- Coding Secure MCP Tunnel ID and Runtime API key;
- Agent Secure MCP Tunnel ID and Runtime API key, if Agent is used;
- ChatGPT custom MCP app connections for Coding and Agent;
- local OpenAI-compatible client Base URL/model/API key, if Agent is used;
- private Git credentials only if the Windows user's existing Git/GitHub setup is not already usable.

Do not migrate Slack App/Bot tokens or Channel IDs into 2.0.

## When should I stay on 1.6.3?

Keep using 1.6.3 when:

- the GitHub + Slack workflow is already stable and meets your needs;
- you cannot or do not want to use the current Secure MCP Tunnel/custom MCP app path;
- a local integration depends specifically on the 1.6.x Slack workflow;
- migration risk is more important than the new Coding/Agent capabilities right now.

There is no requirement to convert a working 1.6.3 installation merely because 2.0 exists. The `1.6.x` branch remains the documentation/source line for that version.
